# Design: Ethical Safeguards (Authorization Gate, Tamper-Evident Audit, Payload Watermarking, RAG Gating)

> Approved design. Revision: `2026-10-31-r1` (retrofit pilot: key table compiled
> from the shipped `specs/026-ethical-safeguards-raii/spec.md` so the mechanical
> contract can be exercised on real Argus artifacts; a green-field feature would
> draft this document BEFORE the spec, per the EGM handoff flow).

## Problem and intended outcomes

Argus has no access-control layer at all: anyone who can start the Studio can
scan any target string the tool accepts, with no recorded authorization and no
tamper-evident accountability trail (the existing `logs/agent_runs/*.json` are
operational state, not audit records). Four proportionate safeguards close the
gap for a single-operator local tool: an explicit authorization acknowledgment
before every scan, a hash-chained audit log, opt-in payload watermarking, and
a RAG ingestion allowlist. Success is observable: a scan cannot start without
the acknowledgment (FR-001), an edited audit line is detected (FR-002), the
default watermarking flag is a byte-identical no-op (FR-003), and an
un-allowlisted document is refused at RAG ingestion (FR-004).

## In scope and out of scope

- **In scope:** authorization-acknowledgment gate (CLI + GUI); append-only,
  HMAC-chained JSONL audit log with verification; opt-in payload watermarking
  helper; RAG trusted-source allowlist check.
- **Out of scope:** full multi-user RBAC (NFR-001), PKI/HSM signing of the
  audit log, automated verification of signed scopes-of-engagement (RSK-01).

## User journeys and behavior

1. The operator starts a scan from the CLI or the GUI; the system requires an
   explicit authorization acknowledgment, records it with a timestamp, and
   only then launches (FR-001, DEC-02).
2. Every tool call and the final risk score land in an append-only audit log
   whose lines are chained with HMAC-SHA256 under a locally stored key
   (FR-002, DEC-01, NFR-002).
3. When `enable_payload_watermarking` is on, generated payloads carry a
   short run-specific marker; when off (the default), payloads are
   byte-identical to today (FR-003).
4. A document added to the RAG knowledge base is embedded only if its source
   is on the configured trusted-source allowlist (FR-004).

## Constraints and quality attributes

- None of the four safeguards may block or meaningfully slow a single-operator
  local scan; no auth servers, HSMs, or multi-tenant models (NFR-001).
- The audit log must not duplicate the operational `logs/agent_runs/*.json`
  data wholesale; it captures the accountability subset only (NFR-002).

## Approved decisions

- DEC-01: audit-line chaining uses HMAC-SHA256 with a locally stored key
  (`AUDIT_LOG_KEY`, bootstrapped via `secrets.token_hex(32)` on first run),
  not a plain unkeyed `sha256(prev_hash + content)` - the 2026-07-10 research
  correction. Justification: an unkeyed chain can be regenerated by anyone
  with filesystem access; the keyed chain raises the bar to "anyone who does
  not also have the key".
- DEC-02: the authorization gate is unconditional (not a feature flag) in
  both CLI and GUI, because an optional authorization gate defeats its own
  purpose; watermarking, by contrast, is explicitly opt-in (`false` default).
- DEC-03: the audit log lives at `logs/audit/audit_<YYYY-MM-DD>.jsonl`,
  separate from the operational `logs/agent_runs/*.json` run-state files.

## Risks and open questions

- RSK-01: FR-001's acknowledgment is a trust-based self-attestation, not
  verified authorization; accepted by the design owner as proportionate.
- RSK-02: the HMAC key lives on the same machine as the log; it protects
  against casual tampering, not a full-machine attacker. Accepted; a
  remote/HSM key is explicitly heavier than this spec targets (NFR-001).

## Traceability Key

| Key | Meaning |
| --- | --- |
| FR-001 | explicit, recorded authorization acknowledgment required before any scan (CLI flag/prompt + GUI checkbox) |
| FR-002 | append-only HMAC-SHA256 hash-chained JSONL audit log with verify_audit_log() |
| FR-003 | opt-in payload watermarking; default off is a byte-identical no-op |
| FR-004 | RAG ingestion gated by a configured trusted-source allowlist |
| NFR-001 | no disproportionate infrastructure or meaningful scan slowdown |
| NFR-002 | audit log captures the accountability subset only, no wholesale duplication |
| DEC-01 | HMAC-SHA256 chaining with locally stored AUDIT_LOG_KEY, not unkeyed sha256 |
| DEC-02 | authorization gate unconditional; watermarking explicitly opt-in |
| DEC-03 | audit log at logs/audit/audit_<date>.jsonl, separate from agent_runs |
| RSK-01 | self-attestation only, no verified authorization (accepted) |
| RSK-02 | same-machine HMAC key, not HSM (accepted) |
