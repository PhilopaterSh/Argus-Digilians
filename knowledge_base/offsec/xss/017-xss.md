# XSS — gapfill_synthetic

- source: gapfill_synthetic
- class: xss

## Scenario

I can inject `<script>alert(1)</script>` into my 'display name' and it executes — but only on my own profile settings page, which only I see. Report as stored XSS?

## Analysis / Response

<think>
It executes, but who is the victim? The payload renders only on a page scoped to the authenticated owner. No cross-user vector: I can only attack myself = self-XSS, non-actionable unless chained (CSRF on the update to set a victim's name, or an admin viewing the value). Check those before dismissing, but as described no privilege boundary is crossed. Triagers reject self-XSS by default.
</think>

**Verdict: Reject — self-XSS (not a vulnerability as described).**

The script executes only on a page visible solely to the account owner, so the only person attackable is the attacker. No boundary crossed, no victim.

**What would change the verdict:**
1. The display name renders to *other* users (comments, admin user-list) → stored XSS. Test those sinks.
2. The profile-update request lacks CSRF protection → attacker could set the payload in a victim's profile → reconsider.

**Severity:** Informational / N/A — CVSS 0.0 as reported.

**Guidance:** don't submit self-XSS alone; most programs mark it OOS/NA. Spend effort confirming whether the name reaches another user's browser — that's the real finding, if it exists.
