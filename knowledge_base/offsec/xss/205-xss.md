## Scenario

Even without PHP execution, how can a file upload lead to stored XSS using Flash (SWF) files?

## Analysis / Response

File uploads can be dangerous even when the server never executes PHP - a crafted file can trigger client-side code. One classic vector is a malicious Flash (SWF) file, because ActionScript running in the victim's browser executes in the uploading site's origin.

The book demonstrates this with ActionScript 2's getURL() function, which can run JavaScript in the page that embeds the SWF:
```
getURL("javascript:alert(document.cookie)")
```
You write a small .as source file containing that call and compile it to a .swf with the open-source MTASC (Motion-Twin ActionScript Compiler):
```
$ mtasc -swf xss.swf -main -header 1:1:1 xss.as
```
If the application lets you upload the SWF and then serves it from its own domain, an attacker who gets a victim to load it runs arbitrary JavaScript in that origin - stealing cookies or performing actions as the victim. This is effectively stored XSS delivered through a file upload.

Defenses: serve all user-uploaded content from a separate, sandboxed domain (so active content can't touch the main origin), set Content-Disposition: attachment and a correct restrictive Content-Type, and validate/strip active file formats. This technique is why uploads of 'harmless' media still need scrutiny.
